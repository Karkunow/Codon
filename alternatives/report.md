# Альтернативи Codon для twirl (2026-11-20, 17:36–17:50 WET)

Запитання: чим замінити Codon 0.20.7 для `original.py` → нативна бібліотека з C ABI без Python, побітово тотожна оригіналу. Усе нижче перевірено сьогодні (URL + цитата або вивід команди); здогадки позначено «гіпотеза, не перевірено».

## Вердикт коротко

Codon — єдиний інструмент із класу «компілятори Python», який одразу дає всі три речі: C-ABI `.dylib` без libpython, прямий виклик `libqiskit` і готовий побітовий паритет з `numpy.random.default_rng` (власний порт PCG64 + SeedSequence + Lemire у stdlib). Усі «Python-компілятори» (Cython, mypyc, Nuitka, Numba, Pythran, Shed Skin, Taichi) відпадають за першим критерієм: їхній вихід потребує CPython. Реальні конкуренти — не компілятори Python, а **переписування на Rust проти крейтів Qiskit** або **C/C++ проти `qiskit.h`**. Рекомендація: лишити Codon зараз, виправити перенесення бібліотеки, і зробити 1-денний прототип на Rust як план Б (деталі нижче).

## Стан екосистеми Qiskit без Python (впливає на будь-який вибір)

- C API офіційно «should be considered experimental… might change between minor version releases» (quantum.cloud.ibm.com/docs/en/api/qiskit-c); 2.4 release notes: «Qiskit's C API is still unstable». Стабільність ABI — пункт роадмапу **2.7** («Declare the C API a stable interface»), ще не випущено; там же «Remove the `libpython` dependency on the standalone `libqiskit` build» — і справді, локальний `libqiskit.dylib` лінкує `python@3.12/…/Python` (`otool -L`, перевірено).
- `qk_circuit_copy`, `qk_circuit_measure`, `qk_circuit_barrier`, `qk_transpile`, `qk_target_*` є; `measure_all` і `remove_final_measurements` немає ні в `funcs.h`, ні в qiskit-cpp (`grep` по `quantumcircuit_def.hpp`, `quantumcircuit_impl.hpp` → порожньо). Тобто ручний порт `calc_final_ops` потрібен у **будь-якому** варіанті, не лише в Codon.
- Подання задач без Python: `qiskit-ibm-runtime-c` — «early prototype… no backwards compatibility guarantees… only supports the Qiskit minor version 2.5»; QRMI — payload-раннер, не Sampler-клієнт. Стабільного Python-free SamplerV2 нема.

## Рекомендація для цього випадку

0. **Спільне обмеження для всіх варіантів**: поки Qiskit 2.7 не прибрав залежність, `libqiskit.dylib` тягне libpython 3.12 (`otool -L`), тож машина-отримувач мусить мати цю бібліотеку Python (не інтерпретатор у процесі). На вибір обгортки це не впливає, але в пакуванні треба врахувати.
1. **Codon лишити** як робочий варіант: він єдиний закриває паритет RNG «з коробки» і вже виміряно дає 9×/17×. Його болі (нема dataclass, винятки абортять процес) уже обійдені кодами помилок у `twirl.codon`.
2. **Негайно полагодити дистрибуцію**: `libtwirl.dylib` посилається на `…/target/release/deps/libqiskit_cext.dylib` абсолютним шляхом (вивід `otool -L`). Лінкувати через `-Wl,-rpath` на `dist/c/lib/libqiskit.dylib` (або `install_name_tool -change`), і перевірити, чи можна статично влити `libcodonrt`/`libomp`, щоб на іншу машину їхала одна `.dylib` + `libqiskit`.
3. **План Б (і, ймовірно, довгостроковий варіант) — Rust `cdylib` проти `crates/cext`/`crates/circuit`**: та сама мова, що й ядро Qiskit; нуль чужих рантаймів; `Result` замість аборту; одна toolchain із `make c`. Ціна: крейти не опубліковані й оголошені «private implementation details», тож це git-залежність на пін Qiskit; плюс ~150 рядків порту PCG64+SeedSequence+Lemire з тестом рівності flips проти `original.py`. Прототип на 1 день, після чого порівняти з Codon за часом і за розміром залежностей.
4. C/C++ проти `qiskit.h` — рівнозначно Rust за можливостями, але без переваги спільної мови з ядром; qiskit-cpp сам експериментальний.
5. Mojo — єдиний «Python-подібний» кандидат з усіма трьома механізмами, але молодий, без паритету RNG і з неперевіреним питанням libpython; не варто зараз.
6. Решта Python-компіляторів виключені за головним критерієм (потребують CPython) — не варто витрачати час.

Наступні кроки: (а) rpath/перелінкування libtwirl; (б) `alternatives/rust-twirl` прототип із тестом побітової рівності flips і probs; (в) стежити за Qiskit 2.7 (стабільний C ABI, `libqiskit` без libpython) — після нього вибір Rust/C стає безпечнішим.
